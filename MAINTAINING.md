# Maintaining mackforge

How the [mackforge.dev](https://mackforge.dev/) site is built and updated.

Browse by project type, filter by topic or platform, or search by name and what the project does. The small theme button switches between the dark and light themes, and remembers your choice on this device.

A separate page, `guides.html`, lists every game guide the [Hintforge](https://github.com/hintforge) organisation has published, alphabetical by game, with a search box.

It is plain HTML, CSS, and small scripts, with no framework, served by GitHub Pages. Both pages remain readable with JavaScript disabled.

## Files

- `index.html` is the project catalogue.
- `guides.html` is the game guides page.
- `sites.html` lists websites and projects by other people. To add one, copy an `<article>` there, put a 1400x875 screenshot of the site in `assets/sites/` as WebP, and update the count. It reuses `guides.js` for the theme and share menu. Its link preview is `assets/sites-preview.png`.
- `style.css` is the stylesheet for both pages and both themes.
- `site.js` handles search, filters, theme choice, and sharing on the catalogue.
- `guides.js` handles the search box and theme choice on the guides page.
- `track.js` sends a [GoatCounter](https://www.goatcounter.com/) event when a visitor follows an outside link, uses the share menu, or downloads a file. GoatCounter's own script, included on every page, counts the page views; it does not count from local previews or when a page is shown inside a frame.
- `guides.json` and `assets/guides/` are generated by `tools/build_guides.py` (the preview images in `assets/guides/previews/` by `tools/build_previews.py`); don't edit them by hand.
- `CNAME` tells GitHub Pages which domain to serve.
- `.nojekyll` tells GitHub Pages to serve the files as they are, without running Jekyll.

## Updating it

The project list is written in `index.html`. Each project has a description, descriptive tags, compatibility labels, and links to its published work. Hintforge is one entry with separate Builder, Reader, and Game guides links.

When adding a project, update its article's filter data and the relevant topic/platform options. The script derives displayed counts from the articles. The agent-manager and memory-tool comparisons are the first two cards in the list, followed by Hintforge; all respond to the filters like every other card. A wide screenshot sits above its card's text; give an article the `portrait` class when its screenshot is a tall phone screen, so the image stays beside the text instead.

The guides page is built from the Hintforge organisation's public repositories. Before publishing, run `python tools/build_guides.py` from the repository root. It needs Python 3 and the GitHub CLI (`gh`, or its full path in the `GH` environment variable), reads the repositories through the GitHub API, copies each guide's status card into `assets/guides/` so the page loads nothing from other sites, and rewrites the cards, count, description and structured data in `guides.html` and the data in `guides.json`. It also writes one page per guide at `guides/<repo>/index.html`, so each game has its own address and title in search results, plus `sitemap.xml` and `robots.txt`. A guide page shows only the guide's README intro and the coverage labels on its status card, never its section titles, which can spoil the game. Don't edit those generated files by hand either. Run the builder whenever a guide goes public. Each guide page's link preview is that guide's own status card: `python tools/build_previews.py` draws every card onto a 1200x630 image in `assets/guides/previews/` (it needs Playwright for Python with Firefox, or Camoufox), then run `build_guides.py` again so the pages point at them. Run both when a guide goes public or its status card changes; a guide without a preview falls back to the shared `assets/guides-preview.png`. The builder and reader repositories are linked once, near the top of the page, rather than as guides; each guide card's title links to that guide's page on this site, and its Guide button to the guide's own repository.

### Walkthrough pages

A guide can also carry a full walkthrough: its Hintforge player's-guide book, shown one page per chapter and appendix at `guides/<repo>/walkthrough/<chapter>/`, with a contents page at `guides/<repo>/walkthrough/`. Unlike the guide itself, these pages show everything in each chapter, so every one of them, the contents page and the guide page's "Full walkthrough" section carry a spoiler notice.

1. Import the book: `python tools/import_book.py <book-folder> <repo>`, where `<book-folder>` holds the book's `*_book.md` and `check.json` and `<repo>` is the guide's repository name in `guides.json`. It copies them to `books/<repo>/book.md` and `books/<repo>/check.json`, and copies nothing when `check.json` is missing or lists a failing chapter. The site only ever reads these in-repo copies.
2. Build the pages: `python tools/build_books.py`. It needs Python 3.12 or later and [Pandoc](https://pandoc.org/) 2.19 or later (the `PANDOC` environment variable, `PATH`, or the Windows installer's folder) and renders each chapter with `tools/book.lua`, which removes the fact-check comments and draws the Tip and Collectibles boxes. It stops without writing anything when a link points at a missing chapter or anchor, two headings would share an address, or book-only markup would reach a page. `--variant a` (one reading column) or `--variant b` (a chapter rail beside the text) picks the layout; both live in `walkthrough.css`, which only these pages load and which has its own `?v=` tag in `build_books.py`.
3. Run `python tools/build_guides.py` afterwards: it adds the "Full walkthrough" section to the guide's page and every walkthrough page to `sitemap.xml`, dated by the book's last commit.
4. Check: `python tools/check_walkthrough.py` follows every link and file reference on the walkthrough pages and checks their link-preview tags and spoiler notice; `python tools/test_build_books.py` runs the import and build refusals on small sample books.

The link preview for the walkthrough pages is `assets/guides/previews/<repo>-walkthrough.png`, a 1200x630 screenshot of the contents page; retake it when that page's look changes. A renamed chapter gets a new address; the old page's folder is not removed by the build.

After a publish is live, run `python tools/indexnow.py` to tell Bing (through [IndexNow](https://www.indexnow.org/documentation), no account needed) to crawl every page in the sitemap; pass URLs to send only those. The text file at the site root named after the key proves the site owns the key, so keep it there.

Open `index.html` or `guides.html` in a browser to preview. The pages themselves need nothing installed.
